# Media Analytics Service — план проекта

Статус: живой документ, версия 0.1  
Дата фиксации: 2026-09-04  
Горизонт первой публичной версии: 8 недель  
Режим работы: около 6 часов в день, 5–6 дней в неделю

## 1. Зачем существует проект

Проект должен стать не просто агрегатором новостей, а объяснимым сервисом медиааналитики:

> Система собирает публикации из источников разных типов, нормализует и классифицирует их, обнаруживает необычные изменения информационного фона и исследует, какие новостные паттерны наблюдались перед значимыми изменениями выбранных экономических или финансовых показателей.

Первая версия не обещает предсказывать рынок и не доказывает причинность. Она помогает человеку быстрее обнаружить событие, увидеть подтверждающие публикации и проверить его на исторических данных.

## 2. Ценность первой версии

Основной пользовательский вопрос:

> Что необычного произошло в информационном поле, с какими темами и сущностями это связано и что происходило с выбранной метрикой в аналогичных исторических случаях?

Практический результат должен выглядеть примерно так:

```text
Тема: crypto regulation
Окно: последние 24 часа
Публикаций: 38
Обычный уровень: 11
Отклонение: +245%

Связанные сущности: SEC, Bitcoin ETF, Coinbase
Изменение BTC/USD за 24 часа: -3.7%

Исторические аналоги: 7
Среднее последующее изменение: -1.8%
Ссылки на исходные публикации: доступны
```

Ценность должна быть проверяема одним из способов:

- пользователь просматривает десятки отобранных событий вместо сотен статей;
- ежедневный обзор готовится заметно быстрее;
- информационный всплеск обнаруживается автоматически;
- исследователь может проверить гипотезу на исторических данных без ручного сведения таблиц.

## 3. Ограничения MVP

Чтобы закончить проект за 8 недель, первая версия ограничивается:

- одной предметной вертикалью;
- одним основным языком публикаций;
- двумя действительно различными типами коллекторов;
- 10–20 заранее определёнными темами;
- одной финансовой или экономической метрикой;
- часовыми или дневными временными интервалами;
- одним основным методом обнаружения новостных всплесков;
- одним методом событийного анализа;
- историческим исследованием вместо прогнозирования.

Окончательный выбор вертикали, языка и метрики должен быть сделан до начала второй недели. Возможный, но пока не утверждённый пример: англоязычные криптовалютные новости и BTC/USD.

## 4. Что сознательно не входит в MVP

- торговые рекомендации и автоматическая торговля;
- утверждения о причинно-следственной связи;
- платёжная система;
- сложная многопользовательская ролевая модель;
- десятки рынков и языков;
- микросервисная архитектура;
- Kafka и Kubernetes;
- большая генеративная модель;
- сторонний LLM API как обязательная часть продукта;
- обучение собственной большой нейросети;
- мобильное приложение;
- обработка миллионов событий в реальном времени.

Добавление технологии допускается только после формулировки проблемы, которую она решает.

## 5. Принципы разработки

1. Сначала законченный вертикальный сценарий, затем расширение платформы.
2. Сначала простая и объяснимая аналитика, затем ML.
3. Исходные публикации и причина каждого вывода должны быть доступны пользователю.
4. Любой аналитический результат должен быть воспроизводимым.
5. Ошибка одного источника не должна останавливать остальные.
6. Повторный импорт не должен создавать дубликаты.
7. Время внутри системы хранится в UTC.
8. Конфигурация и секреты не попадают в репозиторий.
9. Данные, модель, алгоритм и текстовое объяснение результата — разные слои.
10. Корреляция не называется причинностью, а историческое совпадение — прогнозом.

## 7. Границы модулей

### 7.1 `SourcesModule`

Хранит конфигурацию внешних источников:

- имя;
- тип коллектора;
- статус включения;
- конфигурацию подключения;
- расписание или интервал;
- состояние последней успешной обработки.

Источник не должен содержать логику загрузки.

### 7.2 `CollectorsModule`

Содержит адаптеры внешних систем. Все адаптеры возвращают единый нормализуемый контракт.

Черновой контракт:

```ts
type CollectedItem = {
  externalId: string;
  title: string;
  description?: string;
  canonicalUrl: string;
  publishedAt: Date;
  rawPayload?: unknown;
};

interface NewsCollector {
  collect(source: Source): Promise<CollectedItem[]>;
}
```

Предполагаемые реализации MVP:

- RSS/Atom;
- один JSON HTTP API.

Абстракция окончательно фиксируется после реализации второго коллектора, чтобы не проектировать её только по RSS.

### 7.3 `ImportsModule`

Оркестрирует процесс:

- выбирает источник;
- получает подходящий коллектор;
- создаёт запись запуска;
- применяет timeout и политику повторов;
- нормализует элементы;
- выполняет дедупликацию;
- сохраняет новые статьи;
- фиксирует статистику и ошибки;
- обновляет состояние источника только после корректного завершения.

Этот модуль не должен знать формат RSS или конкретного API.

### 7.4 `ArticlesModule`

Отвечает за каноническое представление публикации и доступ к нему. Статья не должна зависеть от формата, из которого она была получена.

### 7.5 `EnrichmentModule`

Отвечает за понимание содержания статьи:

- очистку HTML;
- нормализацию текста;
- определение языка;
- назначение тем;
- извлечение сущностей;
- в будущем — семантическую дедупликацию.

Таксономия тем отделяется от классификатора. Первая реализация классификатора может использовать ключевые слова, но контракт должен допускать последующую замену.

```ts
interface TopicClassifier {
  classify(article: ArticleContent): Promise<TopicPrediction[]>;
}
```

Для каждого результата сохраняются:

- тема;
- confidence;
- метод классификации;
- версия классификатора;
- совпавшие правила или другие объяснения.

### 7.6 `MetricsModule`

Собирает внешний временной ряд независимо от новостей:

- определение метрики;
- адаптер поставщика;
- временные точки;
- интервал;
- источник данных;
- контроль пропусков и повторов.

Первый адаптер обслуживает только одну утверждённую метрику.

### 7.7 `AnalyticsModule`

Получает уже нормализованные данные. Он не загружает RSS, не вызывает внешние API и не классифицирует сырой текст.

Внутренние компоненты:

- `TopicVolumeService` — агрегирует публикации по времени;
- `NewsBaselineService` — считает обычный уровень активности;
- `NewsSpikeDetector` — обнаруживает аномальные интервалы;
- `MetricEventDetector` — находит значимые изменения метрики;
- `PreEventAnalysisService` — исследует окна перед событиями;
- `FindingService` — сохраняет воспроизводимые результаты.

### 7.8 `ReportsModule` или слой представления

Формирует API-ответы и отчёты из готовых findings. Этот слой не придумывает выводы и не выполняет скрытые аналитические расчёты.

## 9. Аналитика версии 1

### 9.1 Временные корзины

Количество статей по теме агрегируется в фиксированные интервалы:

```text
bucket_start | topic            | articles_count
-------------+------------------+---------------
10:00 UTC    | monetary_policy  | 4
11:00 UTC    | monetary_policy  | 5
12:00 UTC    | monetary_policy  | 17
```

### 9.2 Базовый уровень

Для темы рассчитывается rolling baseline по предыдущему периоду. Текущий анализируемый интервал не включается в собственный baseline.

Минимальные показатели:

- среднее;
- медиана;
- стандартное отклонение;
- количество наблюдений.

### 9.3 Информационный всплеск

Первая формула:

```text
z = (current_count - rolling_mean) / rolling_stddev
```

Нужно отдельно определить поведение при нулевом стандартном отклонении и недостатке исторических наблюдений.

### 9.4 Событие метрики

Для цены или индекса анализируется относительное изменение:

```text
return = current_value / previous_value - 1
```

Событием считается превышение утверждённого порога за фиксированное окно. Порог является параметром запуска анализа, а не константой в коде.

### 9.5 Окно перед событием

Для каждого события исследуются публикации до начала изменения:

- наблюдаемая активность темы;
- обычный уровень темы;
- z-score;
- lift;
- наличие других одновременных тем;
- ссылки на статьи, сформировавшие результат.

```text
lift = observed_topic_activity / baseline_topic_activity
```

### 9.6 Защита от ложных выводов

Нужно учитывать:

- look-ahead bias;
- неполные данные;
- различия часовых поясов;
- торговые сессии для традиционных рынков;
- повторные публикации одного события;
- изменение общего числа источников со временем;
- множественную проверку большого количества тем;
- недостаточный размер выборки.

API и UI должны использовать формулировки «наблюдалось», «совпадало», «предшествовало», а не «вызвало» или «предсказывает».

## 10. План на 8 недель

### Неделя 1 — границы продукта и надёжный фундамент

Задачи:

- выбрать первую аудиторию, вертикаль, язык и метрику;
- описать 3–5 пользовательских сценариев;
- определить критерий полезности;
- инициализировать Git и создать корректный `.gitignore`;
- исключить `.env`, `dist`, данные и секреты;
- заменить стандартный README описанием проекта;
- зафиксировать текущую архитектуру и технический долг;
- выбрать механизм миграций PostgreSQL;
- сделать конфигурацию воспроизводимой через `.env.example`;
- определить жизненный цикл подключения к базе;
- зафиксировать решения в первых ADR.

Учебные темы:

- bounded context;
- dependency inversion;
- конфигурация приложения;
- миграции и воспроизводимость окружения.

Критерий недели:

- новый разработчик понимает назначение проекта и может воспроизводимо поднять базовую среду;
- продуктовый сценарий умещается в один абзац;
- список non-goals принят.

### Неделя 2 — контракт коллекторов

Задачи:

- описать жизненный цикл источника;
- реализовать общий результат коллектора;
- привести RSS к новому контракту;
- добавить timeout и ограничение размера ответа;
- нормализовать одиночный и множественный RSS item;
- обработать отсутствующие и некорректные поля;
- реализовать второй тип коллектора;
- только после этого уточнить общий интерфейс и registry/factory;
- добавить ручной запуск импорта одного источника.

Учебные темы:

- adapter pattern;
- polymorphism;
- внешние интеграции;
- ошибки на границе системы;
- SSRF и проверка внешних URL.

Критерий недели:

- два разных типа источников импортируются через один orchestration flow;
- бизнес-логика не содержит проверки конкретного RSS-формата.

### Неделя 3 — надёжный ingestion

Задачи:

- добавить `import_runs`;
- отделить attempt от success;
- сделать ошибки независимыми по источникам;
- определить retry policy и backoff;
- исключить параллельную обработку одного источника;
- сделать импорт идемпотентным;
- уточнить стратегию дедупликации;
- добавить структурированные логи и correlation/import run id;
- определить необходимость очереди задач на основании требований;
- проверить graceful shutdown.

Учебные темы:

- идемпотентность;
- конкурентный доступ;
- блокировки;
- retry и backoff;
- наблюдаемость фоновых процессов.

Критерий недели:

- сбой одного источника не мешает другим;
- повторный запуск безопасен;
- для каждого запуска видны состояние и причина ошибки;
- одновременно не выполняются два импорта одного источника.

### Неделя 4 — enrichment и темы

Задачи:

- очистить и нормализовать текст;
- ввести таксономию из 10–20 тем;
- определить правила изменения таксономии;
- реализовать keyword classifier как первую стратегию;
- учитывать вес заголовка и описания;
- сохранять confidence, метод, версию и объяснение;
- подготовить небольшой вручную проверенный validation set;
- измерить precision/recall хотя бы для основных тем;
- решить, нужен ли локальный классический ML на следующем этапе.

Учебные темы:

- strategy pattern;
- версионирование алгоритмов;
- качество классификации;
- воспроизводимость обработки данных.

Критерий недели:

- статья получает ноль, одну или несколько объяснимых тем;
- повторная классификация новой версией не уничтожает предыдущий результат;
- качество проверяется не только визуально.

### Неделя 5 — сбор финансовой или экономической метрики

Задачи:

Учебные темы:

Критерий недели:

## 11. Предварительный API MVP

Контракты не считаются утверждёнными до проектирования use cases.

```text
POST /sources
GET  /sources
POST /sources/:id/import
GET  /sources/:id/import-runs

GET  /articles
GET  /articles/:id
GET  /topics
GET  /topics/:id/activity

GET  /metrics
GET  /metrics/:code/points
GET  /metrics/:code/events

POST /analysis-runs
GET  /analysis-runs/:id
GET  /analysis-runs/:id/findings
```

Длительный аналитический запуск не обязан завершаться внутри одного HTTP-запроса. Клиент может получить id запуска и отдельно читать его состояние.

## 12. Стратегия тестирования

Текущие scaffold-тесты не являются приоритетом сами по себе. Тесты добавляются вместе с поведением, которое уже должно быть стабильным.

Приоритет:

1. Unit-тесты чистых формул и граничных случаев.
2. Unit-тесты парсинга внешних форматов на сохранённых fixtures.
3. Интеграционные тесты SQL и ограничений базы.
4. Контрактные тесты collector/provider adapters.
5. Небольшое количество e2e-тестов главных сценариев.

Особенно важные случаи:

- пустая и некорректная лента;
- одиночный RSS item;
- timeout;
- повторный импорт;
- одинаковый external id у разных источников;
- нулевое стандартное отклонение;
- недостаточная история для baseline;
- пропуск точки метрики;
- окно анализа на границе диапазона;
- повтор аналитики с той же версией и параметрами.

## 13. Нефункциональные требования MVP

### Надёжность

- один источник не останавливает остальные;
- каждый background run имеет наблюдаемое состояние;
- операции импорта идемпотентны;
- процесс корректно завершает активную работу или оставляет её восстанавливаемой.

### Безопасность

- секреты только через окружение или secret storage;
- URL источников валидируются против SSRF;
- внешние ответы ограничены по времени и размеру;
- административные операции не остаются публичными в развёрнутой версии;
- пользовательский ввод валидируется на границе API.

### Производительность

- сначала измерение и индексы PostgreSQL;
- batch insert вместо последовательных одиночных запросов при подтверждённой необходимости;
- ограниченный параллелизм коллекторов;
- отсутствие неограниченной загрузки данных в память;
- тяжёлые расчёты не блокируют HTTP event loop.

### Наблюдаемость

- структурированные логи;
- import/analysis run id;
- длительность операций;
- fetched/imported/skipped/failed counts;
- понятные причины внешних ошибок.

## 14. Работа на MacBook M1 Pro 32 GB

Локальная целевая среда:

- NestJS;
- PostgreSQL;
- при обоснованной необходимости Redis и worker;
- небольшая локальная NLP/embedding-модель на позднем этапе;
- Docker-образы с поддержкой arm64.

Для MVP отдельный кластер, Kafka, Kubernetes, большая LLM и специализированная аналитическая база не требуются. Основные ограничения ожидаются в качестве данных, диске и запросах, а не в RAM ноутбука.

## 15. Стратегия публичности и интеллектуальной собственности

До восьмой недели основной репозиторий можно сохранять приватным. Перед публикацией проводится отдельная проверка.

Возможная open-core граница:

Публично:

- архитектура и доменная модель;
- collector framework;
- базовые адаптеры;
- API;
- миграции;
- базовая классификация;
- объяснимая статистика;
- тесты и demo dataset.

Приватно при появлении продуктовой ценности:

- коммерческие источники и их конфигурация;
- накопленный датасет;
- размеченные данные;
- точная таксономия и веса;
- продвинутый ranking;
- результаты закрытых экспериментов;
- пользовательские данные.

Если появится действительно новый технический метод, до публичного раскрытия требуется отдельный поиск аналогов и консультация по выбранной юрисдикции. Решение о лицензии принимается осознанно; публичный репозиторий и open source не считаются одним и тем же.

## 16. Учебный режим сотрудничества

Цель — не только выпустить продукт, но и научиться принимать backend-решения.

Рабочий цикл:

1. Формулируем небольшую задачу и критерии приёмки.
2. Автор проекта предлагает дизайн или первую реализацию.
3. Помощник проводит review, задаёт вопросы и объясняет trade-offs.
4. Автор дорабатывает решение.
5. Помощник проверяет поведение и помогает разобрать ошибки.
6. Полная реализация помощником выполняется только по прямой просьбе.

Для каждого заметного решения автор должен уметь объяснить:

- какую проблему оно решает;
- почему выбран этот вариант;
- какие альтернативы рассматривались;
- что станет причиной пересмотреть решение.

## 17. Definition of Done для задачи

Задача считается завершённой, когда:

- сформулировано наблюдаемое поведение;
- обработаны важные ошибки и граничные случаи;
- изменение не смешано с несвязанным рефакторингом;
- есть уместная автоматическая или ручная проверка;
- миграция и конфигурация воспроизводимы, если они затронуты;
- обновлена документация контракта;
- автор может объяснить решение без чтения кода построчно.

## 18. Definition of Done для `v0.1.0`

- выбран один понятный пользователь;
- работают два типа коллекторов;
- импорт устойчив к ошибкам и повторным запускам;
- публикации нормализуются и дедуплицируются;
- статьи получают объяснимые темы;
- собирается одна внешняя метрика;
- обнаруживаются события метрики и информационные всплески;
- выполняется один воспроизводимый pre-event analysis;
- результат связан с исходными статьями;
- основной сценарий доступен через API и минимальное представление;
- критические расчёты покрыты тестами;
- проект запускается по README;
- есть Docker-конфигурация и CI;
- опубликован case study с честными ограничениями;
- принято явное решение о лицензии и границе открытого кода.

## 19. Риски

| Риск | Что делаем |
|---|---|
| Слишком широкий scope | Одна вертикаль, язык и метрика до `v0.1.0` |
| Низкое качество источников | Храним provenance, ошибки и raw metadata |
| Много перепечаток | Сначала deterministic deduplication, затем semantic |
| Ложные корреляции | Baseline, sample size, historical validation, честные формулировки |
| Недостаток истории | Demo backfill и обозначение минимального периода |
| Зависимость от API | Adapter, rate limits, cache/backfill strategy |
| Юридические ограничения контента | Не перепубликуем лишнее, проверяем условия источников |
| Уход в инфраструктуру | Новая технология только под измеренную проблему |
| Проект не доходит до релиза | Scope freeze после шестой недели |
| Помощник делает работу вместо автора | Учебный цикл из раздела 16 |

## 21. Журнал решений

Утверждено:

- **D-001:** первая версия — модульный монолит NestJS.
- **D-002:** PostgreSQL остаётся основной базой.
- **D-003:** внешние LLM API не являются зависимостью MVP.
- **D-004:** аналитика должна быть объяснимой и воспроизводимой.
- **D-005:** проект одновременно является продуктовым прототипом и учебным backend-проектом.
- **D-006:** помощник работает преимущественно как наставник и reviewer.
- **D-007:** решение о публичности и лицензии принимается до релиза, а не автоматически.

Требует решения:

- **Q-001:** первая целевая аудитория;
- **Q-002:** первая предметная вертикаль;
- **Q-003:** основной язык;
- **Q-004:** первая метрика;
- **Q-005:** второй тип коллектора;
- **Q-006:** источник исторических данных;
- **Q-007:** часовой или дневной основной интервал;
- **Q-008:** нужен ли Redis/queue в MVP;
- **Q-009:** формат минимального интерфейса;
- **Q-010:** модель публикации и лицензия.

## 22. Ближайший следующий шаг

Не начинать с нового кода. Сначала подготовить короткий Product Brief:

1. Кто первый пользователь?
2. Какое решение он принимает на основании сервиса?
3. Какие новости он сейчас читает вручную?
4. За какой метрикой следит?
5. Что для него является необычным событием?
6. Как выглядит полезный ежедневный результат?
7. По какому признаку через 8 недель мы поймём, что продукт полезен?

После этого пересматриваются разделы 2–4, выбирается первый вертикальный сценарий и начинается неделя 1.
